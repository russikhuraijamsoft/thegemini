## Current work

The POS screen accepts products from an authorised catalogue caller, with search by name/category ID, category chips, size/combo selection, cart edits, and per-line preparation notes. Category chips filter by the supplied category ID and combine with search. Checkout stays unavailable until an order service is connected. Regression tests cover these interactions and phone-sized layout.

The KDS domain workflow now enforces accepted → cooking → ready → completed, supports cancellation before cooking, and applies the shared inventory deduction only when cooking starts. The Kitchen screen renders authorized tickets, exposes transitions through a persistence callback, and reports missing stock or recipes without advancing the ticket. Branch IDs are required and mixed-branch state is rejected. The existing backend has no branch-scoped inventory data or authenticated KDS API, so the live feed and backend transaction adapter remain unconnected. Legacy records need an explicit branch mapping before migration. Local Flutter tests are unavailable; remote GitHub Actions are the verification source.

The root web workflow had failed at `npm ci` because `package-lock.json` did not match `package.json`. Commit `6c0ffb9` regenerates the lockfile; remote `npm ci` and TypeScript lint pass. The workflow then found a real Node/SSR bug in `appStore.ts` (`navigator` was read at module initialization), now guarded for non-browser execution. Local `npm ci` and `npm run lint` pass. Local Vitest and build cannot start because the Android host does not install Rollup's `@rollup/rollup-linux-arm64-gnu` optional binary; the next remote web run will verify the guard and the suite. The lockfile update does not change application source or declared dependencies.
